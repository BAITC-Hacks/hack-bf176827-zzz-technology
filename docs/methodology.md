# Методология: метрики → роли → кластеры → приоритет

Как инструмент решает «кого из 2 248 клиентов смотреть первым и почему». Всё считается правилами по
структуре графа и суммам; LLM (если включён) только формулирует текст по уже посчитанным фактам.

## 1. Данные и их ловушки

| Особенность выгрузки | Как учтено |
|---|---|
| Обход от 81 seed по **исходящим**, 4 колена | 444 узла 4-го колена без исходящих помечены `truncated`: их исходящие не видны, это не «деньги осели». Они **никогда** не получают роль `terminal`; скор `consolidator` у них ×0.7; приоритет ×0.7; в evidence пометка «исходящие не видны (4-е колено)». |
| Обход **шёл дальше** от узлов 1–3 колена | 1 091 узел с `depth < 4` и без исходящих — подтверждённые стоки (`verified_sink`): от них искали переводы ≥ 5 000 KZT и не нашли. Только они могут быть `terminal`. |
| У seed входящие занижены | Seed не могут быть `transit` (их `pass_through` бессмысленен); в приоритете seed ×0.5 — они уже известны, фокус на тех, кто выше. |
| Порог 5 000 KZT | Дробление ниже порога не видно; в README и карточках это оговаривается как белое пятно. |
| 19 seed без рёбер, 12 seed только получатели | Попадают в выгрузку с ролью `peripheral` и своим `cluster_id`; evidence объясняет причину. |
| 16 слабосвязных компонент | `component_id` в выгрузке; кластеры не пересекают компоненты. |

## 2. Метрики узла (все в `nodes_roles.csv`)

| Метрика | Смысл |
|---|---|
| `in_deg`, `out_deg` | от скольких разных клиентов получил / скольким отправил |
| `in_kzt`, `out_kzt`, `in_tx`, `out_tx` | суммы и число переводов (разные сигналы: 1×4 млн ≠ 40×100 тыс) |
| `pass_through` | `out_kzt / in_kzt`; −1 если входящих нет |
| `pagerank` | взвешенный по сумме PageRank (damping 0.85), своя детерминированная реализация |
| `betweenness` | посредничество на направленном графе (невзвешенное: кратчайший путь «по сумме» для денег не имеет смысла) |
| `n_seed_payers` | сколько seed платят напрямую |
| `n_seed_upstream` | сколько разных seed достигают узла по исходящим за ≤ 4 шага |
| `n_clusters_in` | сколько разных кластеров среди плательщиков |
| `fast_forward_share` | доля исходящего объёма, ушедшего в течение 2 дней после входящего перевода |
| `active_days`, `max_same_day_payers` | активность по датам; синхронные переводы от нескольких плательщиков в один день |
| `in_cycle` | узел входит в возвратный цикл длиной ≤ 5 |
| `repeat_routes` | число устойчивых маршрутов A→B→C через узел (≥ 2 перевода на обоих рёбрах) |

## 3. Правила ролей

Для каждой роли считается скор 0–1 (0 = правило не сработало). Роль = роль с максимальным скором,
`role_score` = этот скор. `peripheral` = 1 − max(остальных): любая роль побеждает только при
уверенности ≥ 0.5. При равенстве порядок: coordinator > consolidator > distributor > transit > terminal > peripheral.

| Роль | Условие (гейт) | Скор | Комментарий |
|---|---|---|---|
| `consolidator` | `in_deg ≥ 3` | `min(1, in_deg/6) × retention`, где `retention = 1 − min(1, pass_through)` (для truncated 0.7); +0.15 если `n_seed_payers ≥ 2` | собирает от многих и удерживает; не зависит от исходящих, поэтому применим к обрезанным узлам с пониженной уверенностью |
| `distributor` | `out_deg ≥ 5` и `out_deg ≥ 2·in_deg` | `min(1, out_deg/30)`; ×0.6 если `in_deg ≥ 3` | веер на многих; двусторонний хаб штрафуется, он ближе к координатору |
| `transit` | не seed, `in_deg ≥ 1`, `out_deg ≥ 1`, `0.7 ≤ pass_through ≤ 1.3` | `0.5 + 0.5·(1 − |pass_through − 1| / 0.3) + 0.2·fast_forward_share` | пришло ≈ ушло; быстрый сквозной транзит повышает уверенность |
| `coordinator` | `in_deg ≥ 2`, `out_deg ≥ 2`, `betweenness ≥ P97`, и (`n_clusters_in ≥ 2` или `n_seed_upstream ≥ 3`) | `0.5 + 0.5·(0.5·min(1, btw/P99) + 0.25·min(1, n_clusters_in/3) + 0.25·min(1, n_seed_upstream/5))` | связывает группы, кандидат в организаторы; формулируется как гипотеза |
| `terminal` | `verified_sink` и (`in_deg ≥ 2` или `in_kzt ≥ 100 000`) | `0.5·min(1, in_kzt/500 000) + 0.5·min(1, in_deg/3)` | деньги пришли и остались, подтверждено обходом |
| `peripheral` | всё остальное | `1 − max(остальных)` | признаков роли нет |

Пороги выведены из распределений на данных: `in_deg ≥ 3` — верхние 5 %, `out_deg ≥ 5` — верхние 5 %,
72 узла с `pass_through` 0.8–1.2, `betweenness` P97 ≈ 1 700 (P99 ≈ 10 000).

Результат на датасете: consolidator 31, coordinator 43, distributor 16, transit 105, terminal 153, peripheral 1 900.

`evidence` — шаблон на роль с числами, ≤ 200 символов, например
`консолидация: получает от 8 плательщиков (из них seed: 2) 2.2 млн KZT, отдаёт дальше 24% (2 получ.)`.
Дополнения: `; в возвратном цикле`, `; устойчивых маршрутов через узел: N`, `; исходящие не видны (4-е колено)`.

## 4. Кластеры

Louvain (`gonum/graph/community.Modularize`, resolution 1.0, фиксированный seed) на **неориентированной
проекции** с весом = сумма переводов в обе стороны. Направление при кластеризации теряется намеренно:
сообщество — это «кто с кем связан деньгами», а направление уже учтено в ролях. Изолированные узлы
получают свои `cluster_id`. Кластеры нумеруются по убыванию размера.

`clusters.csv`: `cluster_id, n_nodes, n_seed, sum_kzt_internal` (рёбра внутри), `top_gids` (топ-5 по
приоритету), `hypothesis`, плюс `component_id`, `sum_kzt_in/out` (потоки через границу), `n_cycles`,
состав ролей. Гипотеза — шаблон по составу ролей (например «признаки сбора с 5 seed через точки
консолидации и веерного вывода»), при включённом LLM переписывается в связный текст по тем же фактам.

На датасете: 88 кластеров (69 сообществ + 19 изолированных seed), 8 с более чем одним seed.

## 5. Приоритет

`priority_score` — взвешенная сумма **перцентильных рангов** (устойчиво к выбросам сумм):

```
0.25·P(in_kzt) + 0.20·P(in_deg) + 0.15·P(n_seed_upstream) + 0.15·P(pagerank) + 0.10·P(betweenness) + 0.15·role_bonus
role_bonus: coordinator = consolidator = 1.0, distributor 0.7, transit 0.5, terminal 0.4, peripheral 0
множители: seed ×0.5 (уже известны), truncated ×0.7 (неполные данные)
```

`top_nodes.csv` — 30 узлов, `why` = evidence + вклад в приоритет (сумма, seed выше по цепочке, PageRank).

## 6. Паттерны (опциональные пункты ТЗ)

- **Возвратные потоки** — простые циклы длиной ≤ 5 (ограниченный DFS, каждый цикл один раз): 468 на датасете; узлы помечаются `in_cycle`.
- **Устойчивые маршруты** — цепочки A→B→C, где на обоих рёбрах ≥ 2 переводов: 736; счётчик `repeat_routes` у среднего узла.
- **Временные паттерны** — `fast_forward_share` (сквозной транзит ≤ 2 дней), `max_same_day_payers` (синхронные переводы), `active_days`.
- **Дробление сумм (детекция аномалий)** — у получателя ≥ 5 входящих переводов и ≥ 60 % из них меньше 15 000 KZT, то есть сразу над порогом выгрузки 5 000: похоже на разбиение крупной суммы на мелкие. Флаг `structuring`, доля `small_tx_share`; на датасете 45 узлов. Правило, не модель: ground truth нет, а суммы ниже 5 000 в выгрузке не видны, поэтому это именно «признаки», требующие проверки.
- **Устойчивость сети** — изъятие top-5/10/20 не-seed узлов по приоритету: доля потерянного оборота, число компонент до/после, размер крупнейшей, сколько узлов лишились всех плательщиков. На датасете изъятие top-20 отрезает 17 % оборота и дробит сеть с 16 до 75 компонент. Доступно и как инструмент ассистента (`remove_nodes`).

## 7. LLM-слой (опционально, OpenAI)

Включается ключом `OPENAI_API_KEY`; без него всё работает на шаблонах. LLM **не назначает роли и не
считает приоритеты** — только:
- переписывает гипотезы кластеров по структурированным фактам (`go run ./cmd/pipeline --llm` или `cmd/ask --hypotheses`; без ключа пайплайн берёт готовые тексты из кэша);
- генерирует справку по узлу из четырёх блоков (`/v1/nodes/{gid}/card`);
- отвечает на вопросы аналитика через инструменты по графу в памяти (`get_node`, `find_nodes`, `who_receives_from`, `who_pays_to`, `path`, `cluster_info`, `top`, `remove_nodes`) и возвращает упомянутые gid для подсветки.

Все ответы кэшируются в `out/llm_cache.json` (коммитится): повторный запуск без ключа и без сети
воспроизводит те же тексты. Промпт требует формулировать гипотезы, ссылаться только на gid и не
выдумывать атрибуты клиентов.

## 8. Ограничения подхода

- Видны только исходящие переводы от seed на 4 колена и только ≥ 5 000 KZT: баланс узла, входящие извне выборки и дробление ниже порога недоступны.
- Роли — эвристики с порогами, а не разметка; ground truth нет, поэтому качество проверяется объяснимостью, а не accuracy.
- Кластеризация на неориентированной проекции; сообщества Louvain зависят от resolution (1.0) и могут дробить крупные группы.
- Betweenness невзвешенный; для 2 248 узлов точный, для больших графов нужна аппроксимация.
- Выводы — гипотезы для проверки, не утверждения о виновности.

## 9. Оценка полноты: каких данных не хватает и что запросить дальше

Выгрузка отвечает на вопрос «куда ушли деньги 81 seed», но не на вопрос «откуда они пришли и что было дальше».
Белые пятна и запросы, которые их закрывают, в порядке ценности:

| Белое пятно | Кого касается | Что запросить у банка / органов |
|---|---|---|
| Входящие переводы seed извне выборки | все 81 seed; 12 из них в данных только получатели, 19 без переводов | входящие seed за июль и 2 месяца до: покажет, кто платит курьерам, и снимет искажение `pass_through` у seed |
| Исходящие у 444 узлов 4-го колена | все `truncated` | обход ещё на 1–2 колена от узлов с приоритетом > 0.5: отделит настоящие стоки от обрезанных |
| Переводы < 5 000 KZT | 45 узлов с признаками дробления, все консолидаторы | полная история этих узлов без порога: подтвердит или опровергнет дробление |
| Только внутрибанковские переводы | консолидаторы и терминалы | межбанковские и наличные операции топ-30: куда деньги уходят из банка |
| Только июль | узлы с `active_days ≥ 20` и координаторы | тот же обход за квартал: устойчивые роли отделятся от разовых |
| Нет типа операции и назначения | топ-30 | назначения платежей и каналы по 30 узлам: проверка деловой цели |

Приоритет запросов задаёт сам топ-лист: первые запросы по top-10, где сходятся несколько seed.
В интерфейсе тот же совет выводится в справке по узлу («На что обратить внимание») и в строке о ближайшем seed.

## 10. Масштабирование до ~1 млн узлов (что изменится)

- **Хранение**: parquet → колоночное хранилище / графовая БД (Neo4j GDS, TigerGraph) или Spark GraphFrames; в памяти Go 1 млн узлов и ~5 млн рёбер ещё помещаются (сотни МБ), но пересчёт всех метрик перестаёт быть секундами.
- **Метрики**: PageRank и степени — линейные, остаются; betweenness O(V·E) → аппроксимация по сэмплу источников (Brandes–Pich) или k-hop локальная; циклы — ограничить длиной 3–4 и искать только вокруг кандидатов.
- **Кластеры**: Louvain → Leiden (быстрее, качественнее), считать по компонентам параллельно.
- **Инкрементальность**: новые выгрузки пересчитывают только затронутые компоненты; фичи узлов хранить в таблице с версиями.
- **Интерфейс**: не рисовать весь граф — отдавать ego-подграфы и агрегаты по кластерам, серверная раскладка.
- **LLM**: инструменты остаются теми же, меняется только источник данных (запросы к БД вместо памяти).
